# 沉浸式翻译字幕兼容设计

## 问题

YouTube 播放器中已经显示由“沉浸式翻译”生成的双语字幕，但视频笔记仍记录为空字幕。当前内容脚本只读取 YouTube 原生 `.ytp-caption-segment`。沉浸式翻译会隐藏原生字幕节点，并把字幕显示在自己的字幕容器中，因此现有选择器无法获得画面中的文本。

## 目标

- 读取沉浸式翻译当前可见的双语字幕。
- 同时保留原文和译文，按画面顺序换行保存。
- 沉浸式翻译字幕不可用时，继续读取 YouTube 和哔哩哔哩原生字幕。
- 同一帧只采集一个字幕来源，避免重复内容进入前置字幕块。
- 保持前置字幕开关、5/10/20/30 秒范围和编辑能力不变。

## 方案

把页面字幕文本读取逻辑提取成独立、可测试的模块。读取时按以下优先级选择首个有可见文本的来源：

1. 沉浸式翻译字幕容器 `.imt-captions-text`，依次读取其中的 `.source-cue` 与 `.target-cue`。
2. YouTube 原生字幕 `.ytp-caption-segment`。
3. 哔哩哔哩原生字幕 `.bpx-player-subtitle-panel-text` 与 `.bilibili-player-video-subtitle`。

沉浸式翻译容器适用于 YouTube 和哔哩哔哩。每个节点继续使用可见性判断；空节点会被忽略；同一来源中的重复相邻文本会合并。已有字幕缓冲、时间窗口和长度限制继续负责跨时间去重和截取。

## 测试

- 先添加失败用例，证明现有逻辑无法读取沉浸式翻译的原文和译文。
- 验证双语文本按原文、译文的顺序保留。
- 验证沉浸式翻译容器优先于被隐藏或仍存在的原生字幕，避免双份内容。
- 验证沉浸式翻译为空时会回退到平台原生字幕。
- 运行完整测试、构建和打包检查。
- 在 Edge 重新加载 worktree 构建，播放带双语字幕的视频并创建标记，确认独立字幕块出现实际文本。

## 范围

本次只修复已显示字幕的 DOM 读取兼容性，不接入平台字幕接口，不扫描播放器中的任意文字，也不改变已有笔记数据结构。
